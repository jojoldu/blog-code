# 2~3년 뒤에도 백엔드 개발자를 뽑을까?

AI가 발전하면서 백엔드 개발자의 역할이 사라질 거라는 이야기를 자주 듣는다.
AI 코딩 도구를 만드는 Cursor는 빌링 엔지니어를 뽑고 있다.

2~3년 뒤에 백엔드 개발자라는 포지션이 어떻게 될지 생각할 때, 가장 먼저 확인해볼 만한 건 AI 모델을 직접 만드는 회사들의 채용공고였다.

OpenAI의 한 엔지니어는 공식 행사에서 토큰을 원하는 만큼 쓰면서 Codex를 실험할 수 있다고 했다.
앤트로픽의 8월 보고서에는 외부에 공개하지 않은 프론티어급 모델도 사내 코딩과 연구에 쓰고 있다고 적혀 있었다.

우리가 앞으로 더 좋은 모델을 더 많이 쓸 수 있게 됐을 때의 개발 환경을 이 회사들은 먼저 경험하고 있다고 생각했다.
그런 환경에서 어떤 업무를 개발자에게 맡기고 어떤 경험을 채용 기준으로 삼는지 살펴보면, 우리도 다음에 무엇을 준비할지 힌트를 얻을 수 있지 않을까.

그래서 그 회사들이 백엔드 엔지니어를 계속 채용하는지, 채용한다면 어떤 일을 맡기는지 확인해보기로 했다.

Cursor의 공고에는 사용량 기반 과금 시스템을 실제로 운영해본 경험과, 고객의 잔액과 크레딧을 기록하는 원장을 만들거나 유지보수해본 경험이 적혀 있었다.
OpenAI와 앤트로픽도 결제와 과금을 맡길 백엔드 개발자를 찾고 있었다.

우리 회사에서도 AI를 활용해 개발자가 아닌 분들이 코드에 기여할 수 있도록 이것저것 시도해보고 있다.
근데 주문과 결제, 정산 로직은 전문 백엔드 개발자분들이 다루고 있다. 틀리면 큰일 나는 영역이니깐.
이런 영역에서는 전문가가 AI를 함께 써서 더 안전하게 처리하고 생산성도 높이는 데 집중한다. 반면 덜 위험하고 언제든 롤백할 수 있는 부분에서는 좀 더 과감하게 시도하기도 한다.

AI로 코드를 빨리 만들 수 있어도, 잘못 청구한 돈을 바로잡거나 틀어진 재고를 복구하는 일은 여전히 필요하니깐.
구현 비용에 그때의 손실과 복구 비용까지 따져보면, 그 업무를 아는 백엔드 개발자가 AI를 활용해 설계와 운영을 맡는 편이 더 경제적일 수 있겠다는 생각이 들었다.

그래서 결제와 정산 외의 공고도 더 찾아봤다. AI를 만드는 회사뿐 아니라, 기존 사업에 AI를 적용하는 기업들도 함께 봤다.
지금까지 백엔드 개발을 하며 쌓은 경험으로 다음에 어떤 일을 해볼 수 있을지 여섯 가지로 묶어봤다.

1. 도메인 특화 엔지니어

중복 요청으로 같은 주문이 두 번 처리되거나, 결제는 됐는데 이용 권한이 생기지 않는 문제를 해결해본 경험이 여기에 쓰인다. 결제와 정산, 예약과 재고처럼 업무 규칙이 복잡하고 잘못 처리했을 때 손실이 큰 시스템을 맡는다.

OpenAI는 백엔드나 분산 시스템을 설계하고 운영해본 경험을 요구했다. 중복 요청과 동시성 문제를 다루고, 데이터가 틀어지거나 일부 처리가 실패했을 때 어떻게 복구할지 판단할 수 있어야 했다. 결제 경험이 없더라도 분산 시스템을 깊이 다뤄본 경험이 있는 엔지니어를 환영한다고 적혀 있었다.

대표공고: OpenAI: Staff & Software Engineer, Payments & Billing, Consumer Monetization
Anthropic: Staff+ Software Engineer, Billing Platform
AWS: Software Development Engineer, Billing Data Services
Cursor: Software Engineer, Billing

2. 플랫폼 엔지니어

기존 사용자의 로그인이 끊기지 않게 인증 시스템을 이전해본 경험은 앤트로픽의 Auth & Identity 공고에서 요구하는 경험 중 하나다. OAuth나 역할 기반 접근 제어를 다뤄본 경험도 보고 있었다.

인증과 권한, 문자와 이메일 발송, VOD처럼 여러 팀이 함께 쓰는 서비스와 API를 만드는 방향이다. 주문 서비스와 학습 서비스가 같은 메시지 발송 API를 쓰게 만드는 일도 여기에 해당한다. 앤트로픽 공고에는 다른 팀이 쉽게 사용할 수 있도록 문서와 도구를 제공하는 능력도 적혀 있었다.

대표공고: OpenAI: Backend Software Engineer, Applied Foundations
Anthropic: Staff+ Software Engineer, Auth & Identity

3. 대규모 데이터 처리 엔지니어

주문 이벤트로 매출을 집계하는데 데이터가 늦게 들어오거나, 중단된 작업을 다시 돌리면서 같은 주문이 두 번 집계되는 일이 생길 수 있다. 데이터를 모으고 가공하는 동안 이런 문제가 생겨도 서비스와 분석에서 믿고 쓸 수 있게 만드는 일이다.

배치 작업이나 데이터 파이프라인을 운영해봤다면 그 경험을 더 키워볼 수 있다. OpenAI의 Data Engineer 공고는 분산 데이터 처리와 저장 시스템 경험을 요구했다. Spark 코드를 작성하고 오류와 성능 문제를 해결할 수 있어야 했고, Airflow 같은 도구로 처리 작업을 관리해본 경험도 필요했다.

대표공고: OpenAI: Data Engineer
Google: Software Engineer III, Google Cloud, Dataform

4. AI 시스템 엔지니어

사내 문서를 찾아 답하는 챗봇을 붙였는데, 프롬프트를 고친 뒤 잘 답하던 질문에서 틀린 답이 나오거나 응답이 너무 느려질 수 있다. 자사 서비스와 사내 업무에 LLM과 에이전트를 적용할 때 이런 문제까지 다룬다.

월마트는 분산 시스템을 만들고 운영한 경험과, AI 모델이나 LLM API를 실제 서비스에 연동해본 경험을 요구했다. 결과를 평가하고 지연 시간과 비용을 관리하며, 실패했을 때의 처리 방법까지 설계할 수 있어야 했다. API를 연동하고 장애에 대응해온 경험에 LLM의 결과를 평가하는 경험을 더해볼 만한 방향이다.

대표공고: Walmart: Staff, Software Engineer
Google: Web Solutions Engineer, Technology and Insights Partnership Systems, YouTube India

5. 프로덕트 엔지니어

서버를 만든 뒤 실제로 쓰는 사람에게 기능이 도움이 됐는지 확인하고, 화면과 사용 방식까지 고쳐보고 싶다면 이쪽도 있다.

OpenAI의 프로덕트 엔지니어 공고는 React와 TypeScript로 화면을 만들고, 실제 서비스의 API와 데이터 모델을 설계해본 경험을 함께 요구했다. 고객의 문제가 명확하지 않은 상태에서도 무엇을 만들지 판단하고, 구현부터 출시와 개선까지 맡아본 사람을 찾고 있었다.

대표공고: OpenAI: Product Engineer, Full Stack - Agents
Anthropic: Senior Software Engineer, Full-stack
xAI: Member of Technical Staff - Grok Product

6. FDE(Forward Deployed Engineer)

고객사 시스템에 API를 연동하면서 데이터와 권한, 업무 규칙까지 확인해봤다면 FDE가 하는 일도 살펴볼 만하다. 고객의 업무와 기존 시스템을 파악하고, 자사 기술을 그 환경에서 쓸 수 있도록 구현하고 배포한다.

앤트로픽은 LLM 서비스를 만들고 평가해 운영 환경에 배포해본 경험과 Python 개발 역량을 요구했다. 고객의 업무를 직접 파악하고, 기술적인 내용을 여러 직군이 이해할 수 있게 설명하는 능력도 채용 기준에 들어 있었다.

대표공고: OpenAI: Forward Deployed Engineer (FDE) - Seattle
Anthropic: Forward Deployed Engineer

앞의 네 가지는 시스템을 설계하고 운영하는 경험을 더 쌓는 쪽이고, 뒤의 두 가지는 제품과 고객 업무까지 맡아보는 쪽이다. 프로덕트 엔지니어와 FDE는 백엔드 전용 포지션은 아니지만, 백엔드 개발자가 맡는 일을 넓혀볼 수 있어 함께 넣었다.

공고들을 살펴보고 나니, AI가 더 발전하면 백엔드 개발자가 할 일은 없어질 거라는 생각에는 동의하기 어려웠다. AI를 적극적으로 쓰는 회사들도 어떤 업무를 이해하고, 어떤 시스템을 설계하고 운영해봤는지를 여전히 구체적으로 묻고 있었다.

각 방향을 준비하는 데 도움이 될 강의도 수업 내용을 확인해 인프런 기획전으로 모아보려 한다.

첫 후속 글에서는 결제와 과금 공고를 자세히 보려고 한다. 결제 도메인 경험이 없어도 내세울 수 있는 경험은 무엇인지, 무엇을 더 준비해야 할지부터 살펴보려 한다.
개인 프로젝트로 작은 구독 서비스를 만든다면 중복 요청이나 응답 유실을 어떻게 재현하고, 청구 내역과 이용 권한이 맞는지 어디까지 확인해봐야 할지도 함께 정리해보려고 한다.
